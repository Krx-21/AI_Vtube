# C09-sdk — Neuro Game SDK / API protocol
Verdict counts: {'confirmed': 35, 'likely': 1, 'disputed': 2}

## Summary A (evidence hunter)
This is the best-evidenced cluster in the whole project, and much of it should be graded T1 rather than T2: I pulled every file in VedalAI/neuro-sdk verbatim via curl and checked the GitHub commit API, which shows that API/SPECIFICATION.md, API/README.md, API/VOICE_CHAT.md, API/BEST_PRACTICES.md and CHANGELOG.md were all last written by Vedal987 himself (19–21 Aug 2026 commits "Add voice chat support" / "Update docs"), so their text is Vedal's own words under the rubric's T1 definition, not merely org-published artifact. Established at T1: the game interface is a single plaintext-JSON WebSocket where the game describes state in text and Neuro emits named actions with JSON-schema-shaped arguments that the game must validate itself ("The data parameter comes directly from Neuro, so there is a chance it might be malformed"); a ~20-second server-side timeout on action/result; automatic (limited-count) retry of a whole actions force on success:false; a low/medium/high/critical priority field that can interrupt her speech (17 Dec 2025); a startup acknowledgement exposing characterId "neuro"/"evil" and displayName (1 Jul 2026), making Evil Neuro a first-class addressable identity at the protocol level; and an optional second WebSocket at /game/<name>/voice carrying 48 kHz mono Float32-LE PCM with game-supplied per-speaker attribution and server-side STT/TTS (19 Aug 2026). Also T1, and new to the claim list: Vedal's own Feb 2025 statement that the backend "doesn't keep track of individual connections… it's mostly stateless", that plaintext-only is a websocket-library limitation he can work around, that game start/stop automation is "one of the main use cases for this SDK", and that he can "rewrite/censor stuff I need to for Neuro automatically" backend-side; plus BEST_PRACTICES' disclosures that action names are scoped to the character and shared across concurrently connected integrations, that context survives disconnects, and that the voice loop is "a full cognitive cycle (seconds, not milliseconds)". What remains unknown: the SDK is client-side documentation only — no server code, no model, no prompt template, no memory implementation is published, so nothing here reveals which LLM, how context is stored, or what runs on the May 2026 server. PROPOSALS.md (game-automation shutdown messages, reregister_all) is T2 and was authored by maintainer Alexejhero in Dec 2024, remains explicitly unshipped, and must not be cited as live behaviour. Finally, the SDK's text-only nature is scoped to SDK-integrated games only: osu! and Minecraft run through separate vision-based modules, so "the SDK has no vision" is not the same statement as "Neuro has no vision".

## Summary B (skeptic)
This is the best-evidenced cluster in the whole project and it survived adversarial checking almost intact: I re-pulled all seven official docs (README, CHANGELOG, API/README, API/SPECIFICATION, API/VOICE_CHAT, API/BEST_PRACTICES, API/PROPOSALS) verbatim from raw.githubusercontent.com and confirmed nearly every quoted string word-for-word. Crucially, the GitHub commits API shows SPECIFICATION.md, BEST_PRACTICES.md and VOICE_CHAT.md were last authored by Vedal987 himself (6b79780 on 19 Aug 2026; 86af943 on 20 Aug 2026; 6cae304 on 21 Aug 2026), so the ~20s action/result timeout, the silent-ignore rule, speech_finished, the retry-on-failure rule and the whole voice-chat wire format are T1 (Vedal's own writing), not merely T2 org output. Established at T1/T2: the Neuro Game API is one plaintext-JSON WebSocket (C2S {command, game, data?} / S2C {command, data?}) on which games register named actions with a restricted-subset JSON schema, push text context, and receive discrete action messages whose `data` is explicitly unvalidated LLM output the game must check — i.e. a tool-calling loop with a hard ~20s synchronous result wait; plus, since 19 Aug 2026, an optional second WebSocket at /game/<name>/voice carrying 48 kHz mono Float32-LE PCM with game-supplied speaker attribution and server-side STT/TTS. The `startup` ack (1 Jul 2026) exposes characterId `neuro`/`evil` and displayName, making Evil Neuro a first-class addressable identity at the protocol level. Three things needed correction: the 'action force concurrency' story (Vedal's Feb 2025 'process both at once and merge' remark is explicitly untested and is superseded by Vedal's own Aug 2026 BEST_PRACTICES text saying a second force 'can cancel and replace' the first, and by his adjacent quote 'Neuro can't think about two things at once'); the 'two independent sources call it tool calling' framing (only ktrain5169's docs make that analogy — the nikechan.com post contains no tool/function-calling language at all); and 'the SDK is text-only', which stopped being true on 19 Aug 2026 when a binary audio side-channel shipped. What remains unknown from this cluster alone: which LLM, STT or TTS the server runs (never named anywhere in the repo), whether the voice-chat 'server' is the same process/host as the LLM loop, whether Neuro and Evil share a model, and whether the unshipped PROPOSALS (reregister-all, graceful/immediate shutdown, shutdown-ready) are live in the private backend — the file says flatly that they 'do not exist yet'.

## Contradictions resolved
- Contradiction #2 (action-force concurrency) — RESOLVED, three statements describe three different things at three different dates. (a) SPECIFICATION.md's 'Neuro can only handle one action force at a time… will cause problems' is a warning to integrators, not a scheduler description. (b) Vedal's 22 Feb 2025 'she would independently and simultaneously process both requests at once and the two states should be merged back afterwards' is prefaced by 'I really don't think you should do this' and 'this is untested', and he says in the same breath 'Neuro can't think about two things at once' — so it is aspirational branch-and-merge, never validated. (c) The 'strictly serial' quote is about CONTEXT arriving mid-decision, a different message type, and it is the one that survived into shipped docs: BEST_PRACTICES.md (Vedal, Aug 2026) says 'The server holds it and delivers it in order once the result arrives.' The authoritative current answer is BEST_PRACTICES.md's newer wording: 'Send one force at a time and wait for its resolution: a new force while another is in progress can cancel and replace it.' Cancel-and-replace, not parallel-merge. Report as: serial with an ordered server-side queue; the parallel-merge idea is an untested 2025 aspiration that the 2026 docs contradict.
- Contradiction #10 (game-vision misattribution) — RESOLVED for this cluster's half. The SDK is text-only and contains no image, screen-capture or vision message of any kind in any of its five API documents; the only binary channel is voice PCM. That is a fact about the SDK pathway ONLY and must not be generalised into 'Neuro has no vision'. Neuro's osu! and Minecraft play run on separate, non-SDK vision modules (NeuroWiki: osu! and Minecraft each 'with the help of a specialized AI module'; the Dec-2024 Minecraft AI 'relies heavily on visual recognition'), and the 80x60 grayscale figure belongs to the osu!/Minecraft module lineage, not to the SDK. The report should present two disjoint game-playing pathways: (1) SDK-integrated games = text state in / named actions out; (2) bespoke vision modules for osu!/Minecraft. NeuroWiki also notes the game modules 'have limited interaction with her broader AI systems'.
- Contradiction #1 (turn latency) — PARTIALLY RESOLVED with new T1 evidence from this cluster. VOICE_CHAT.md, authored by Vedal987, states the voice loop 'Hearing → speech-to-text → decision → text-to-speech is a full cognitive cycle (seconds, not milliseconds)'. Combined with the ~20 s action/result timeout and BEST_PRACTICES' 'Every second of delay is a second Neuro spends frozen waiting', this supports the 1–3 second end-to-end figure for a full perceive-think-speak cycle and shows the sub-second figures must be measuring a narrower segment (e.g. LLM first token), not audible response.
- Clone-contamination flag #7 (Gary described as 'a backend implementation for the Neuro-sama SDK') — RESOLVED. The phrase comes from VedalAI's own README ('Gary is another backend implementation for advanced use'), where 'backend' means a simulator server that speaks the game-facing side of the protocol for testing, under the section headed 'Useful if you're building a simulator server for testing purposes' and behind the explicit 'we do not review, verify, or endorse' disclaimer. Gary (local Llama) and Jippity (OpenAI) are test doubles; neither says anything about Neuro's model. VOICE_CHAT.md independently confirms their test-tool status: 'Testing tools (Randy, Tony) do not implement it.' The report must never render Gary as 'a backend implementation of Neuro'.
- Clone-contamination flag #9 (the Neuropilot/Neuroscope strategic-layer-plus-telemetry-layer split) — RESOLVED as community integrator design, not Vedal's backend. The high-level/low-level split IS officially sourced — the VedalAI README says games needing non-low APM 'will not work well without Neuro only controlling the high-level actions and letting another system decide how to handle the low-level actions' — but the specific Neuropilot/Neuroscope layering and the Outer Wilds illustration are one community developer's pattern for adapting real-time games to the protocol. Cite the README sentence for the architectural principle; do not cite the blog's layer names as Neuro internals. (Separately note that 'NeuroPilot' is also the name of a real community VSCode plugin Neuro uses for coding — a different thing, and a naming collision the report should avoid.)
- Clone-flag correction touching this cluster's evidence grade: claims resting on VedalAI/neuro-sdk API documents should be graded T1, not T2, because the GitHub commits API shows SPECIFICATION.md, API/README.md, CHANGELOG.md, VOICE_CHAT.md and BEST_PRACTICES.md were all last authored by Vedal987 himself in Aug 2026. Conversely API/PROPOSALS.md must be DOWNGRADED to T2: its sole commit is by maintainer Alexejhero (11 Dec 2024) and its own header says the messages 'have not been implemented yet… for all intents and purposes, they do not exist yet', so the game-automation/process-termination material is design intent, not shipped behaviour — though Vedal separately endorsed the intent at T1 in discussion #58.
- Contradiction 2 (action-force concurrency) — RESOLVED in favour of the serial reading, with a date fix. Vedal's Feb 2025 'she would independently and simultaneously process both requests at once and the two states should be merged back afterwards' is explicitly prefixed 'I really don't think you should do this' and 'this is untested', and the very next sentence of the same comment says 'Neuro can't think about two things at once'. His second quote ('she can only process one thing at once... the context will be merged after she is finished making her decision') is the unhedged one. Eighteen months later, Vedal's own BEST_PRACTICES.md (21 Aug 2026, 'verified against the current server') states the actual behaviour: 'Send one force at a time and wait for its resolution: a new force while another is in progress can cancel and replace it, as the spec warns.' Report wording: the decision step is serial; a second in-flight force cancels and replaces the first; the parallel-and-merge description was speculative, untested, and is superseded by 2026 documentation.
- Contradiction 10 (game-vision misattribution) — PARTIALLY RESOLVED from this cluster's side.
